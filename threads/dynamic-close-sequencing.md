# Does any shipped product re-plan the close when an input is late, or is the checklist a fixed gated list?

Status: live
Opened: session 0008B
Yield: 1.8 (0009C C33 experience, partly noise)
Touches: C33, C32, C19; threads/what-replaces-the-checklist
Sources: [seq-oracle-fccs-task-predecessors], [seq-oracle-fccc-task-manager-tutorial], [seq2-sap-afc-overall-delay-kpi], [seq2-langgraph-interrupts-wait-indefinitely], [seq2-langchain-planning-agents-replan], [seq2-cohnreznick-cpapa-faster-close-survey], [seq2-extend-close-without-chasing], [seq2-cfodive-liveflow-data-bottlenecks]

What we know so far (0008B explorer, diagram-half turn, Direction review 0005 item 4): shipped close task managers gate, they do not re-plan. Oracle FCCS predecessors: Finish to Start default ("starts as soon as the predecessor task completes or finishes with warning"), Finish Error to Start option, Finish to Finish blocks completion. Oracle Task Manager tutorial: "Pending tasks cannot open until their predecessor task closes, even if their start date is reached"; delinquency emails; parent dates roll up from children. No date recompute, no reorder. SAP Advanced Financial Closing: uncompleted predecessor causes an error (learning quiz only, not entered). FloQast Dependencies help behind Cloudflare (snippet: soft/hard blocking of sign-off per entity, no cascade). No close vendor doc and no agent orchestrator doc found showing self re-planning against a dependency graph.

Implication (not a claim yet): an agent that finishes its tasks early does not shorten the close where a person-held input gates successors; the close's critical path stays the slowest human input (C32 chasing), and C33's checklist survives as a fixed gated list, not a schedule. A late input produces a delinquency email to the owner, not a re-ordered plan.

What it would take to become a claim: one shipped product (close or general agent orchestrator) documenting automatic re-sequencing or re-dating when a predecessor is late, or a close benchmark showing days-to-close set by the last human input rather than by preparation time (e.g. a case where reconciliations auto-certify on BD1 yet close ends BD5 waiting on accrual inputs).

Open sub-questions:
- Do agent orchestrators (Copilot Studio, Agentforce, LangGraph) document re-planning on failed or late steps?
- Which close input is most often the gating late item (accrual confirmations, intercompany, bank)?

Draft claim (0009B, not kept):
> ## C57. Close agents will shorten the close only as far as the slowest input held outside finance, because the shipped close schedulers hold a task until its predecessor closes and report the delay rather than re-plan around it, and no re-plan can produce a missing figure, so after agents the controller's lever on days to close is a cutoff at which the agent books an estimate for each late input, not a faster preparer.
>
> The schedulers gate. Oracle's close task manager states that pending tasks cannot open until their predecessor task closes, even if their start date is reached, and that users are notified by e-mail for delinquencies. SAP's closing app defines the end of the cycle as the end of whichever task list ends latest, computes which task will cause delay, and lets the user follow up through SAP Jam or emails so that the responsible agent can speed up. Agent frameworks do the same: a LangGraph interrupt waits indefinitely until execution is resumed with a response, and LangChain's re-planning agents re-plan only after a step has run, which reorders work but cannot create the accrual input a budget owner has not sent. The waiting is where the time goes: 56% of finance professionals in a 2025 benchmark named dependency on other departments as a top obstacle, and a 2014 survey of CFOs put waiting for information from other people first among the factors that kept the close long.
>
> This disagrees with the re-planning design LangChain describes as the remedy for a plan that did not have the desired effect, because in the close the dependency is on a figure, not on an order of work. Consequence: the controller sets a cutoff for each outside input, as a spend vendor's policy that expense reports submitted after the 2nd are processed in the following month already does; at the cutoff the agent posts the estimate, the preparer works the true-ups when the late inputs arrive, and the delay report names departments rather than accountants. Signpost: a close vendor shipping automatic estimate-at-cutoff for late inputs before automatic re-dating of tasks confirms; a benchmark showing days to close falling at agent adopters while the share blaming waits on other departments holds counts for it.
