# After one vendor's mid-year model update misstates the same accrual class at hundreds of audited customers in 2030, close agents from 2031 are pinned to one model version for a whole fiscal year, the way payroll runs on one year's tax tables

In July 2030 a close vendor moves its agents to a new model version mid-year, as vendors routinely did, and the new version starts classifying a common type of software subscription prepayment as an immediate expense. It does this with higher confidence than the old version, so at every customer that had moved that accrual class to confidence routing the items post above the threshold with no person looking. The year-end blind samples show the problem in January 2031, and several hundred audited companies find the same misstatement in the same class in the same quarter, a few of them large enough to restate. The finding that changes the market is not that a model was wrong; it is that a vendor's update changed a control at every customer at once with none of them approving it. By the end of 2031 auditors treat the model version as part of the control, and close agents run on one model version per fiscal year, chosen and tested at the start of the year and changed only at year end after a parallel run, the way payroll runs on one year's tax tables. Model providers sell long-term-support versions to finance vendors with support windows of three years, and the newest model never touches a close until the next fiscal year begins.

Mechanism: Today close vendors update the model behind their agents without customer approval, and model providers retire versions on cycles shorter than a fiscal year plus its audit. Customers move recurring classes to confidence routing (C21) and measure error rates with small annual blind samples (C12). A mid-year update that shifts one judgment in one class produces the same error at every customer, above every threshold, and the samples catch it only at year end. Auditors respond with the rule they already apply to settings (C26): a model change is a change to the control, so the evidence restarts, and a change mid-year leaves two half-years of evidence instead of one full year. Vendors cannot run a separate change approval at each of thousands of customers mid-year, so they pin versions to the fiscal year, and they move more work into frozen rules (C14), which no model update touches.

The controller stops accepting vendor model updates silently and starts making an annual decision: which model version to adopt for the coming year, after reading the vendor's parallel-run results on the company's own prior-year data. The external auditor adds the model version to its testing of changes to automated controls, and in the first quarter tests that the version in production all year matches the one approved. The vendor's product team stops shipping capability continuously and ships it once a year, in a release timed to its customers' fiscal year ends, and keeps four or five model versions running at once for customers with different year ends.

What would settle it: a close vendor's terms stating whether model changes require customer approval; an auditor's methodology treating a vendor model change as a program change; a model provider offering a support window longer than eighteen months to regulated customers.

Signposts: a close vendor offering version pinning or an annual release by 2028; a model provider publishing a long-term-support tier for finance or other regulated uses; a reported misstatement traced to a vendor model update, in any audited company, before 2031; failing signpost, auditors in the 2027 to 2029 audits accept vendor model updates without treating them as changes to the customer's controls and no correlated error appears.
